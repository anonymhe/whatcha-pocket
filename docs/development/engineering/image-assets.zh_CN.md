# 图片素材：格式选择与转换

本固件的 53 个图片源全部以 LVGL I8 索引色位图发布。RGB565A8 时占用 881.9 KB，索引色后占用 347.2 KB，在 3 MB 应用分区里省下 535 KB。本文记录格式如何工作、什么情况下值得用，以及两个会悄悄毁掉索引色转换的缺陷。

## 1. 两种存储格式

| | RGB565A8 | I8 索引色 |
| --- | --- | --- |
| 每像素字节 | 3（2 字节 RGB565 + 1 字节 alpha） | 1 字节索引 |
| 固定开销 | 无 | 1024 字节调色板（256 × `lv_color32_t`） |
| 颜色数 | 65,536 色 × 256 级 alpha | 255 色（索引 0 为透明） |
| 解码 | 直接指向 Flash，不占 RAM | 行缓冲，`w * 4` 字节 |
| 96 × 96 精灵的成本 | 27,648 B | 10,240 B |

`tools/gen_images.py` 负责在两者之间转换。两种格式都是普通的 `lv_image_dsc_t` 变量，素材切换格式时页面代码无需改动。

## 2. 小图标要不要转，由收支平衡点决定

1024 字节调色板是每个文件的固定开销，所以索引色只有在像素总数足以摊薄它时才更小。解 `3n² = 1024 + n²`，平衡点约在每边 22.6 px：

| 精灵尺寸 | RGB565A8 | I8 | 结果 |
| --- | --- | --- | --- |
| 16 × 16 | 768 B | 1,280 B | 索引色**更大** |
| 22 × 22 | 1,452 B | 1,552 B | 索引色**更大** |
| 24 × 24 | 1,728 B | 1,600 B | 索引色更小 |
| 96 × 96 | 27,648 B | 10,240 B | 索引色省 63% |

首页那六个 22 × 22 图标正好卡在尴尬位置：每个涨了 100 B，整组净增约 0.6 KB。它们仍然一并转换，是为了让素材管线保持单一格式，且这点损失相对任何更大尺寸的收益都微不足道。**今后新加小于 24 px 的图标不必再转。**

## 3. 索引色数据长什么样

`bin_decoder` 把 map 数组当作「调色板 + 索引行」。有三处极易写错，且每一处都只会在运行时静默出错：

- **调色板在前，且恒为 256 项。** 不论实际用了多少色，`LV_COLOR_INDEXED_PALETTE_SIZE(I8)` 都是 256，所以数组总是以 1024 字节调色板开头，索引数据从偏移 1024 起。
- **`lv_color32_t` 是 `{blue, green, red, alpha}`**，不是 RGBA。写成 RGBA 会让每张素材的红蓝通道对调，而画面看起来依然像一张正常的图，所以这个错误能扛过肉眼扫一眼。
- **索引行按 `stride = (w + 3) & ~3` 补齐。** `emit()` 里的行距必须与 `LV_DRAW_BUF_STRIDE(w, cf)` 由 `CONFIG_LV_DRAW_BUF_STRIDE_ALIGN` 算出的值一致。`sdkconfig.defaults` 把该选项钉为 1，避免上游改动让每一行整体错位。

索引 0 必须完全透明（`0,0,0,0`），这也是量化器绝不能对可见像素输出 `0` 的原因。

## 4. 只有一个开关关闭时，解码才不占 RAM

LVGL 会把索引色图转成 ARGB8888 再交给软件渲染器混合。走哪条路径决定了这件事是否免费：

- `CONFIG_LV_BIN_DECODER_RAM_LOAD=n`（本仓库已钉死）经 `get_area_cb` 逐行解码，只需一个 `w * 4` 行缓冲。96 × 96 精灵的临时 RAM 是 384 B。
- `CONFIG_LV_BIN_DECODER_RAM_LOAD=y` 每次打开都分配 `w * h * 4`。同一张图要 36.9 KB，而本板 64 KB 的 LVGL 池经不起几次这样的分配。

该选项默认是 `n`，但上游没有任何保证，所以 `sdkconfig.defaults` 里显式写明。构建通过完全不能说明这件事：代价只在运行时、页面打开的那一刻才出现。

## 5. 量化美术图：让高频色保持精确

像素画由少数主色加上抗锯齿边缘处的渐变长尾构成。一张 96 × 96 的图可能有 650 种颜色，其中 340 种只出现一次。

按像素数排序、保留前 255 种，可以让所有高频色零误差，于是平坦区域和描边分毫未动，只有长尾被合并。这正是这次转换能被接受的原因：误差落在图像本来就在过渡的地方。

## 6. 合并时 alpha 的权重必须高于颜色

把长尾色并入最近的调色板项需要一个距离度量。四个通道等权时，一个半透明边缘像素会并进邻近的**不透明**色，从而丢掉覆盖率：叠加到面板背景上，这些像素会跳变 218–224/255。

把 alpha 权重提到每个颜色通道的 4 倍可以解决大部分。对 38 张有损图实测，alpha 误差超过 32/255 的像素从 288 降到 187，合成误差从 258 降到 229，代价是平坦区域的 RGB 误差略升，而这是正确的取舍：覆盖率跳变看得见，单像素的颜色偏移看不见。把 alpha 从度量里完全去掉会让两项都大幅恶化（1,521 像素），所以方向很关键。

## 7. 两个会悄悄毁掉转换的缺陷

两个都是本仓库初版实现里踩到的，症状都是「图看起来是坏的」而不是「图有点偏」，所以任何新写的量化器都要检查：

- **长尾色默认落到了调色板槽位 0。** 零初始化的 `slot` 数组让未合并的颜色停在索引 0，而那是透明。某张精灵有 833 个像素被从画面里打孔打掉，而不是取一个近似色。每个可见色都必须显式赋 `slot >= 1`。
- **距离平方和在 `int16` 里溢出。** 单个通道差 253 的平方是 32,761，加上三个通道就回绕成负数，`argmin` 于是挑中任意项。490 个待合并色里有 424 个落到了错误的槽位，这就是黑色像素变灰的原因。这类运算必须用 `int32`，任何超过 32,767 的和都可疑。

## 8. 度量用户看到的东西，而不是原始通道

逐通道与原图比较会高估损失。真正上屏的是图像叠加在面板背景之后的样子，所以该引用的是那个数：

```bash
python3 tools/gen_images.py --verify
```

它按图报告可见像素中 RGB 或 alpha 偏差超过 32/255 的比例，基准是从 git 历史里找回的转换前原版。当前状态：53 个源里 15 个逐像素完全一致；其余 38 个合成后 164,432 个可见像素中有 229 个（0.14%）超过 32/255，单图最差 0.87%，单图平均误差不超过 2.2/255。

`--verify` 是差异报告，不是质量门，因为调色板合并本身就是有损的。只有当上面的阈值变成硬预算时，才该把它接进 CI。

## 9. 仍然需要真机确认的部分

数值上说得通、画面上未必对，有两类情况值得在硬件上看一眼：

- **缩放绘制的精灵。** `page_sync.c` 以半尺寸绘制 19 张 `cha_*`，`page_muyu.c` 在动画里压扁 `art_muyu_*`。LVGL 的软件变换会插值相邻像素，而源图里有 1,503 个 `alpha == 0` 却带颜色的像素，其颜色被归到了调色板槽位 0。边缘可能渗色，只有实屏能定论。
- **最差的几张。** `cha_duck` 与 `art_1024_win` 的单图误差最大。这两张若看着干净，其余基本不会出问题。

## 10. 新增一张图

```bash
# 把新的 .c 放进 main/assets/images/（images/ 由 file(GLOB) 自动纳入）
python3 tools/gen_images.py --check    # 报告体积与颜色数，不写文件
python3 tools/gen_images.py            # 转换，超过 255 色的图会被拒绝
python3 tools/gen_images.py --force    # 连有长尾的像素画也转
python3 tools/gen_images.py --verify   # 按图报告与原版的差异
python3 tools/check_material.py        # 确认每个素材都有引用
```

每边小于 24 px 的图不值得索引化，保持 RGB565A8。超过 255 色的新素材只有在长尾确实是渐变噪声时才转，`--verify` 加看一眼原图能回答这个问题。
